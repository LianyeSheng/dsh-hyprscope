# Observation and capability contract

English | [中文](/docs/cli/PROTOCOL.zh.md)

This document fixes the meaning of the fields `hyprscope` outputs, and records the capability boundary of the control surface (`hyprscope control`). The observation layer's fields are the `dsh-cua` provider's input; the capabilities that change the desktop are exposed only through `hyprscope control`, never from the read-only commands.

Renaming a field counts as a breaking change and requires updating the tests and the README in the same change.

Read commands accept `--desktop user|agent|external` to select the instance they observe; `user` is the default and therefore also the value used when the flag is omitted. The selector grants nothing: observation stays read-only, and the default user resolution skips the recorded agent or external instance, so a running managed desktop cannot silently become the user's desktop.

## 1. Snapshot record

The top level of `state --json`:

| Field | Meaning |
|---|---|
| `readOnly` | Always `true`. Callers use it to refuse to treat this source as an executable backend |
| `observedAt` | ISO-8601 capture time |
| `session` | Discovery result: `instanceSignature`, `waylandDisplay`, `pid`, `runtimeDir`, `instanceCount`, `discovery` (`explicit`/`scan`), `waylandDisplaySource`, `inheritedEnvironment` |
| `compositor` | `name`, `version`, `branch`, `configProvider` (`lua`/`hyprlang`), `backend` |
| `isolation` | `mode: 'shared-seat'`, `seatCount` (filled only by `doctor`), `note` |
| `active` | `window`, `workspace`, `monitor` |
| `monitors` / `workspaces` / `clients` / `layers` | Normalized arrays |
| `cursor` | `{ x, y }`, global layout coordinates |
| `lock` | `{ locked: boolean \| null, source, sessionId, seat, type, reason? }` |

The stable fields of `clients[]`:

```
windowId            Hyprland window address (0x…), the unique id for later operations
app                 window class
initialApp          class at startup
title               title (mutable, not an id)
pid                 client process
monitor             monitor id (number)
workspace           { id, name }, or null
position            { x, y }, global layout coordinates
size                { width, height }, logical pixels
floating            whether the window floats
fullscreen          internal fullscreen mode: 0 normal / 1 fullscreen / 2 maximized (a number, not a boolean)
fullscreenClient    client-side fullscreen mode, encoded like fullscreen
pinned / grouped    pinned / number of windows in the group
mapped / hidden / acceptsInput / xwayland
focusHistoryId      focus-history ordinal, 0 is the most recent
stableId            stable identifier generated by Hyprland
```

`monitors[]`: `id`, `name`, `position`, `size` (including `scale`, `transform`, `refreshRate`), `focused`, `dpmsOn`, `activeWorkspace`, `specialWorkspace`, `reserved`.
`workspaces[]`: `id`, `name`, `monitor`, `windows`, `hasFullscreen`, `lastWindow`, `lastWindowTitle`, `persistent`, `layout`.
`layers[]`: one entry per surface, `monitor`, `level`, `namespace`, `pid`, `position`, `size`, `alpha`.

## 2. Coordinates and scaling

- All geometry is **global layout coordinates**, with the origin at the top-left of the layout; with multiple monitors it can be negative.
- `size` is logical pixels, not physical pixels: a 4K output with `scale = 2` has a logical size of 1920×1080.
- Screenshot resolution = the output's physical pixels. Region screenshots use global layout coordinates; `grim` accepts `X,Y WxH`, and this tool converts `x,y,w,h` into that format.
- When a monitor has a `transform` (rotation), region coordinates are still given as layout coordinates; the compositor handles the conversion.
- When pointer input is implemented later, it must use the same coordinate system; do not use the physical pixels of a screenshot directly as layout coordinates.

### 2.1 Screenshot record

`screenshot --json` returns:

| Field | Meaning |
|---|---|
| `path` | Absolute path of the PNG that was written |
| `bytes` / `width` / `height` | File size and the PNG's pixel dimensions |
| `sha256` | SHA-256 of the PNG file |
| `capturedAt` | ISO-8601 capture time |
| `source` | Where the capture came from: `{ monitor, region, scope, window }` |

`source.scope` is `layout`, `monitor`, `region` or `window`. For a window capture `source.window` is `{ identifier, appId, title }`, where `identifier` is the foreign-toplevel identifier the compositor reported (Hyprland reports the window's stable id in hex), `appId` is the window class and `title` the title at capture time; `source.monitor` and `source.region` are null. For the other scopes `source.window` is null.

A window capture selects exactly one of `--window-id <0x… address or foreign-toplevel identifier>`, `--window-app <class>` or `--window-title <exact title>`; it cannot be combined with `--monitor` or `--region`. An ambiguous `--window-app` or `--window-title` exits 2 and lists every candidate with its `0x…` address, application id, workspace, title and whether it is on the active workspace or off-screen, telling you to pass `--window-id` to pick one. An explicit `--output` is preflighted before any capture: its directory must already exist and be writable, otherwise the command fails with `SCREENSHOT_FAILED` and the hint to pass `--output <writable path>` (the default cache directory is created first). The compositor renders that one toplevel, so a window on another workspace or covered by another window can still be captured; only mapped windows can be captured, the cursor is not composited, and a window with a `no_screen_share` rule or a denied screenshot permission yields the compositor's denied placeholder. The path needs the native `bin/wl-capture` helper (`pnpm run build:capture`) and a compositor that advertises `ext-image-copy-capture`, `ext-foreign-toplevel-list` and `ext-image-capture-source`; if the helper is missing the command says to build it. Layout, monitor and region captures keep using `grim`. A window capture is still a read-only observation: no lease or capability baseline is involved.

The locked-session rule is unchanged for every scope: a screenshot is refused by default while the session reports locked, and `--allow-locked` permits it.

## 3. Event stream

`.socket2.sock` is line text in the format `event>>payload`, where the payload is comma-separated fields. `events` only parses and passes through:

```
workspace>>2
activewindow>>zen,Title
openwindow>>0x1234,2,zen,Title
closewindow>>0x1234
movewindow>>0x1234,2
monitoradded>>HDMI-A-1
```

`events` defines the match string as `event:data` (a colon), so `--match '^openwindow:'` matches only window-open events. When `--once` finds no match before the timeout it exits with code 1, which makes scripted waits convenient.

## 4. Error codes

| Code | Trigger condition | Caller handling |
|---|---|---|
| `USAGE` | Invalid arguments | Fix the arguments; exit code 2 |
| `NO_SESSION` | No instance found / no socket for the named display | Ask the user to start the compositor or pass `--signature` |
| `SESSION_GONE` | The control socket or the event socket has disconnected | Rediscover; do not retry the old handle |
| `READ_ONLY` | A command outside the allowlist was requested | Programming error; do not fall back |
| `COMMAND_FAILED` | `hyprctl`/probe exited non-zero | Look at `details.stderr`/`details.exitCode` |
| `BAD_OUTPUT` | The return is not JSON | Version incompatibility; record `details.sample` |
| `LOCKED` | The session reports locked and `--allow-locked` was not passed | Wait for the unlock; do not retry the screenshot |
| `SCREENSHOT_FAILED` | `grim` or the window capture helper (`bin/wl-capture`) failed or produced no PNG | Check `WAYLAND_DISPLAY` and the session |
| `TIMEOUT` | Timeout | Input already sent cannot be undone (during `hyprscope control run`) |
| `CAPABILITY` | A plan (or an approval request) needs a capability the accepted baseline does not grant, or no baseline is accepted yet | Run `hyprscope control baseline --probe` (a widening probe asks the host for a confirmation card), then replan; do not retry |

## 5. Capability report

The `capabilities` of `doctor --json`:

```json
{
  "observation": ["screenshot", "events", "clients", "workspaces", "monitors", "layers", "cursor", "lockState"],
  "action": [],
  "wayland": {
    "seatCount": 1,
    "globals": [{ "interface": "zwp_virtual_keyboard_manager_v1", "version": 1 }],
    "capabilities": { "virtualKeyboard": true, "virtualPointer": true, "screencopy": true, "imageCopyCapture": true,
      "foreignToplevel": true, "workspaceManager": true, "idleNotifier": true, "sessionLock": true, "pointerWarp": true }
  }
}
```

`action` is always empty; this is the read-only entry's promise, not a pending item: `hyprscope` does not change the desktop, and control capabilities appear only under `hyprscope control` (§8, §9). A `null` `wayland` means the probe is not compiled.

`doctor --json` also carries an `environment` block describing the runtime the control surface needs; doctor only inspects it, and never spawns the overlay, creates a file or writes anything:

```json
{
  "environment": {
    "overlay": { "binary": "quickshell", "path": "/usr/bin/quickshell", "available": true, "source": "default", "hint": null },
    "state": { "path": "/home/user/.local/state/hyprscope", "exists": true, "writable": true, "probe": "/home/user/.local/state/hyprscope", "reason": null },
    "capture": { "window": "window capture asks the compositor for the toplevel (ext-foreign-toplevel-list), so it also works for a mapped window on an inactive workspace or off-screen; it does not need the window to be visible, and the PNG carries the window size, not the output size" }
  }
}
```

`overlay` is the Quickshell binary the consent overlay would start: `binary` is `quickshell` unless `HYPRSCOPE_QUICKSHELL` overrides it, `source` says which of the two it is, `available`/`path` come from a PATH lookup, and `hint` carries the actionable fix when it is missing. `state` is the `$XDG_STATE_HOME/hyprscope` directory shared by the baseline, lease and desktop records; `exists` says whether it is already there, and `writable` (`true`, `false`, or `null` when it cannot be determined), `probe` and `reason` report whether a file could be created there — checked on the directory or its nearest existing ancestor with `access(W_OK)`, without creating or deleting anything. `capture.window` is the one-line semantics of window capture: the compositor renders the toplevel, so a mapped window on an inactive workspace or off-screen is captured too; the PNG carries the window size, not the output size. The human-readable report prints the same facts under an `environment` heading.

### 5.1 Capability baseline

`doctor --json` also reports which desktop it observed and the capability baseline `hyprscope control` gates on for that desktop (see [COMPATIBILITY.md](/docs/cli/COMPATIBILITY.md) and [BASELINE.md](/docs/cli/BASELINE.md)). `doctor` only reads the accepted file: it never probes, writes, or takes a lease.

```json
{
  "target": { "kind": "agent", "signature": "…", "managed": true },
  "baseline": {
    "present": true,
    "state": "usable",
    "path": "/home/user/.local/state/hyprscope/desktop/baseline/<signature>.json",
    "approvedAt": "2026-11-17T23:12:00.000Z",
    "compositorVersion": "0.57.2",
    "target": "agent",
    "staleness": {
      "verdict": "fresh",
      "reasons": [],
      "measuredAt": "2026-11-18T00:05:00.000Z",
      "differences": []
    },
    "degraded": [],
    "missingRequired": [],
    "warnings": []
  }
}
```

`target` is the resolved desktop: `kind` is `user`, `agent` or `external`, `signature` is the live instance signature, and `managed` is true only for a recorded agent or external desktop. `baseline.target` repeats the kind the baseline belongs to. `baseline.staleness` compares that baseline with the running instance: `verdict` is `fresh`, `stale` or `unverified`; `reasons` are human sentences; `measuredAt` is the comparison time; and `differences[]` lists disagreements as `{ field, recorded, observed }`, with values as text. `staleness` is `null` when no accepted baseline exists. `stale` means a recorded value differs or the live instance could not report it; `unverified` means the baseline does not record a value the comparison needs, including an older baseline written before effective values were recorded.

`present: false` with `state: null` means control is unavailable even though observation still works; `warnings[0]` then carries the reader's reason (no file, still a draft, unreadable, or a newer schema). `missingRequired` lists required capabilities the baseline did not measure, and `degraded` lists safety paths that are absent; currently the only degraded capability is `safety.failsafe-bind`. Neither list changes `capabilities.observation` or `capabilities.action`.

The user's desktop keeps the machine-wide `baseline.json`; an agent or external desktop is keyed by its instance signature under `desktop/baseline/<signature>.json`, so one desktop's baseline cannot gate another. A `stale` or `unverified` verdict is a report here; `hyprscope control run` refuses it with `CAPABILITY` before any consent step.

## 6. Mapping to `dsh-cua`

`dsh-cua`'s request union lives in `packages/experimental/cua/src/protocol.ts`. "The read-only layer" here means `hyprscope` itself: the table below only says whether it can provide a method; what the control side can already do is listed in §9, and the CUA provider has not been wired up yet.

| CUA method | Can the read-only layer provide it | Notes |
|---|---|---|
| `getCapabilities` | Partially | Use `doctor`'s platform/version/isolation; `permissions` comes from the lease state (§8) |
| `listApps` / `findApps` | Yes | The `pid` in `clients[]` plus the `.desktop` file can assemble an app list |
| `listWindows` | Yes | `clients[]`, with `windowId` as the Hyprland address |
| `activate` / `show` | No | The control side already implements them with `focusWindow` / `workspace` (§9) |
| `getState` | Partially | Only window geometry and focus; no accessibility element tree (Wayland has no global AX, that needs AT-SPI) |
| `getState`'s `tree` / `elementId` | No | AT-SPI is separate work |
| `screenshot` | Yes | `grim` for layout/monitor/region; `ext-image-copy-capture` for one window; returns size/sha256/path |
| `mouseMove` / `click` / `drag` / `scroll` | No | The control side already implements them through `wl-inject` (§9) |
| `pressKey` / `typeText` / `paste` | No | Keyboard injection is implemented (§9); the clipboard is not yet |
| `setValue` / `selectText` / `performAction` / `invoke` | No | Depends on the AT-SPI element tree |

Three points to watch when mapping:

1. CUA coordinates default to "the pixels of the most recent screenshot", and `relative: true` is a 0–999 per-mille value; this tool gives layout coordinates. Do the conversion in the provider and do not pollute the observation layer.
2. CUA's `snapshotId`/`elementId` have no counterpart; judge invalidation yourself from `focusHistoryId` + `windowId` when window geometry changes.
3. CUA's `appLevelAccessibility: false` is the honest value for a Linux provider; do not report true.

## 7. Version-sensitive points

- Hyprland 0.57's `dispatch` argument is a **Lua expression** (for example `hl.dsp.focus({ window = "address:0x…" })`), not the old dispatcher name; `keyword` has no effect under a Lua configuration, and configuration changes go through `eval`. The tool supports only the Lua provider: when `configProvider` is not `lua`, the whole control subset is unavailable (corresponding to `dispatch.lua` in [COMPATIBILITY.md](/docs/cli/COMPATIBILITY.md)).
- `hyprctl -j cursorpos` returns `{"x","y"}` on 0.57; older versions may return plain text `x, y`, and the parser must tolerate that.
- The format of `hyprland.lock` is `<pid>\n<wayland-display>`; reading only the first line also works, and the display falls back to scanning.
- Event names grow with versions (`ext_workspace_manager_v1`-related ones, `screencopy`, and so on); consumers must ignore unknown events rather than error.
- Single-window capture requires the compositor to advertise `ext-image-copy-capture`, `ext-foreign-toplevel-list` and `ext-image-capture-source`; Hyprland 0.57.2 does.

## 8. Control lease (`hyprscope control`)

The lease answers **control ownership**: who is in control and when it ends. The lease itself does not inject input; injection and plan execution are in §9. The observation layer's `readOnly` and `action: []` semantics therefore stay unchanged: `hyprscope` still sends no command that changes the desktop, and `doctor` still reports no control or input capability.

Read the control side's state with `hyprscope control status --json` (`phase`, remaining time, holder/overlay pid, recovery progress); the record format is in "Lease record" below.

### Lease record

The single source of truth is `$XDG_STATE_HOME/hyprlease/state.json` for the user's desktop; an agent or external desktop keeps the same record under `$XDG_STATE_HOME/hyprlease/<signature>/state.json`, selected internally by `HYPRSCOPE_LEASE_SIGNATURE`. The fields are the same:

| Field | Meaning |
|---|---|
| `leaseId` | Opaque lease id; every decision/control record must carry it |
| `phase` | `consent` / `granted` / `released` / `denied` / `expired` / `revoked` |
| `reason` | The request reason shown to the host |
| `planBound` / `planSummary` | Whether the lease approves a submitted plan, and the consent-card summary; `false` / `null` when no plan is bound |
| `attempt` / `maxResumes` | The current attempt (`0` is the original plan, `1..maxResumes` are recoveries) and the recovery count consent covers (default `1`, maximum `3`) |
| `totalBudgetMs` | The total budget counted from `createdAt`, or `null` (unbounded) |
| `renewals[]` | One `{ at, attempt, ttlMs, expiresAt }` per renewal, in time order |
| `ttlMs` | The single-hold time requested at request time; a renewal changes only `expiresAt`, not this field |
| `consentDeadline` | The consent phase deadline; when it passes the lease becomes `expired` automatically |
| `grantedAt` / `expiresAt` | Grant time and expiry time |
| `endedAt` / `endReason` | Terminal time and reason (`agent` / `host` / `shortcut` / `ttl` / `stale-owner` / `consent-timeout`) |
| `requesterPid` / `holderPid` / `overlayPid` | The three related processes; the holder is the owner after approval |

The heartbeat `heartbeat.json` is refreshed every 500ms by the requester/holder; when it has not been refreshed for more than 5 seconds the lease is treated as ownerless, and the next `status` or `run` closes the lease out as `revoked`.

### Invariants

1. Single lease: `lease.lock` is created with `O_EXCL`, and a second lease request gets `LEASE_ACTIVE`.
2. Terminal states are irreversible: after entering `released/denied/expired/revoked` the lease never returns to `granted`.
3. Record ownership: `decision.json` / `control.json` carry `leaseId`; records that do not belong to the current lease are ignored.
4. No input replay: queued actions are never executed after control is returned; input already sent cannot be undone (once injection is enabled).
5. Forced close-out: if `panic` sees no holder close-out within 5 seconds, it stops the overlay, writes the terminal state, and releases the lock itself.
6. Renewal does not re-ask for consent: `renewLease` only renews a lease that is `granted`, unexpired and has the same `leaseId`; `attempt` increments by one each time and never exceeds `maxResumes`, while `planBound` and `planSummary` stay unchanged (details in `docs/cli/LEASE.md`).

### Failsafe shortcut

`hyprscope control install-bind` appends a marked block with three `hl.bind(...)` calls to `~/.config/hypr/hyprland.lua`. The failsafe bind's argument is `hl.dsp.exec_cmd("<absolute node> <absolute bin/hyprscope.ts> control panic --source shortcut")`, plus `description = "hyprscope failsafe: revoke desktop control"`. The desktop-message bind (default `SUPER + ALT + M`, `--message-key` overrides it) runs `hyprscope message open` and carries `description = "hyprscope message: open the desktop composer"`. The desktop-annotate bind (default `SUPER + ALT + A`, `--annotate-key` overrides it) runs `hyprscope message annotate` and carries `description = "hyprscope: desktop annotate"`. The installation flow: check the three keys are distinct and none is taken → back up the configuration → write the block → `hyprctl reload` → verify all three descriptions in `hyprctl binds -j` → record the message and annotation keys in the message state directory (`shortcut.txt`, `annotate-shortcut.txt`) → on failure restore the backup and both shortcut records, remove the generated Lua file and report `BIND_FAILED`.

Write the key name in Hyprland's spelling (`Escape`, not `ESC`); in 0.57 `hl.bind` records the internal index rather than the command string in `arg`, so verification can only look at `description`.

### Relationship to CUA

CUA's `click` / `typeText` and other methods are still unimplemented, and `getCapabilities().action` must not report them as available. The precondition for a future injection helper is: read the lease before every batch of actions and continue only when `phase === "granted"` and the `leaseId` matches; after a lease reaches a terminal state, reject all injection.

## 9. Plan execution (capability declaration)

`hyprscope` remains read-only. The only command that changes desktop state is `hyprscope control run <plan.json | ->`: it must hold a lease from §8 that is bound to the submitted plan (`planBound: true`). `hyprscope control install-bind` only writes the Hyprland configuration file and does not change desktop state, and the `hyprscope message` surface only paints overlays and writes message and annotation session files, so neither is a control path.

Plan execution, interference prompts, the recovery model and fault records are in `docs/cli/PLAN.md`; whether these capabilities still hold after switching machines or versions is in [COMPATIBILITY.md](/docs/cli/COMPATIBILITY.md) (the capability baseline, implemented and gated at run time).

New capability surface:

| Capability | Wayland protocol / interface | Notes |
|---|---|---|
| Absolute/relative pointer motion | `zwlr_virtual_pointer_manager_v1` → `motion_absolute` / `motion` | Single seat, interleaved with the physical pointer |
| Pointer buttons | Same manager → `button` | Clicking absolute coordinates is a low-confidence action |
| Scroll | Same manager → `axis` + `frame` | Values in `wl_fixed` |
| Keyboard keys and text | `zwp_virtual_keyboard_manager_v1` → `keymap` / `key` / `modifiers` | Fixed US keymap, keycodes are evdev |
| Focus / workspace switching | `hyprctl dispatch '<lua 表达式>'` | The test machine's compositor uses the Lua config provider, and the `dispatch` argument is evaluated as Lua; only the allowlisted subset the executor generates is executed: `hl.dsp.focus({ workspace = … })` / `hl.dsp.focus({ window = … })` |
| Window move / size | Same subset: `hl.dsp.window.move` / `hl.dsp.window.resize` | Absolute layout coordinates (`x`/`y`; when resizing, `x`/`y` are width/height); the expression carries no `relative` field — in the Lua API a missing `relative` means absolute, and the tool never generates a relative move; when a window is fullscreen the compositor rejects both calls |
| Window float / pin | Same subset: `hl.dsp.window.float` / `hl.dsp.window.pin` | Set the state explicitly: `action = "on" \| "off"`, not a toggle |
| Window fullscreen state | Same subset: `hl.dsp.window.fullscreen_state` | `internal` / `client` each take `0` (normal) / `1` (fullscreen) / `2` (maximized), with `action = "set"` |
| Move silently to a workspace | Same subset: `hl.dsp.window.move` + `follow = false` | `follow = false` does not switch the current workspace; this is a capability of the dispatcher subset, and no plan op maps to it yet |

The plan ops `resizeWindow` (absolute `width`/`height`) and `fullscreenWindow` (`internal`/`client` modes) map to the window-size and fullscreen-state calls respectively; `floatWindow`'s `floating`/`pinned` map to explicit `on`/`off`.

The injection helper additionally requires a lease proof: `--lease-state <state.json> --lease <id>`; it re-reads the state file before each injection and rejects that command when `phase` is not `granted`, the id does not match, the lease does not approve a submitted plan (`planBound` is not `true`), or the lease has expired; `--probe` and `--dry-run` are unaffected.

Lua expressions are assembled by the executor from allowlisted templates, with variables format-checked first (window address `0x…`, workspace name `[A-Za-z0-9._-]`, coordinates are integers); no string is passed through verbatim. If the compositor returns `error:` or `warning:`, it counts as a failure.

Explicitly not provided: `exec`, `keyword`, `kill`, `plugin`, arbitrary dispatchers, arbitrary Lua, shell commands, configuration changes. The only `hyprctl reload` is in `install-bind`, used solely to make the managed shortcuts take effect.

The plan record (`out/runs/<runId>/`) is not part of the observation contract; its fields evolve with the executor. Only the fault-record fields listed in `docs/cli/PLAN.md` carry a stability commitment to callers.
## 10. Desktop-message surface (`hyprscope message`)

`hyprscope message` is neither observation nor control: it owns the hint/composer overlay and the files a running DSH Host reads. It takes no lease, changes no desktop state and contributes no observation fields.

`open` (`--json`) returns `{ command: "open", dir, overlay: { pid, log }, request: { nonce, at }, dsh: "available" | "unavailable" }`; `annotate` returns the same shape with `command: "annotate"` and `request.mode: "annotate"`; `overlay` returns `{ command: "overlay", dir, overlay }`; `stop` returns `{ command: "stop", dir }`. `--lang zh|en` selects the language of the overlay this command starts (default `zh`, or `HYPRSCOPE_LANG`). Files live in `$XDG_STATE_HOME/hyprscope/message` (or `HYPRSCOPE_MESSAGE_DIR`): the Host writes `status.json`, `ack.json`, `last-session.json` and `overlay.log`; the CLI writes `open.json` and `quit.json`; `hyprscope control install-bind` records the message and annotation keys in `shortcut.txt` and `annotate-shortcut.txt`; and the overlay writes one JSON document per message into `outbox/`. The overlay is a Quickshell process started with `-n`, so repeated calls keep one instance; a missing compositor is `NO_SESSION` and a missing Quickshell is `OVERLAY_FAILED`. An annotate request has its own session files, documented in §11. The DSH plugin half and the injected message shape are in [docs/plugin/DSH-PLUGIN.md](/docs/plugin/DSH-PLUGIN.md).

## 11. Desktop annotation session (`hyprscope message annotate`)

`hyprscope message annotate` asks the running DSH Host for one desktop annotation session: a frozen screenshot, freehand shapes, push-to-talk speech and a short review card. The CLI starts the same single-instance Quickshell overlay as the composer and writes one `open.json` request with `mode: "annotate"`; a request without `mode` is still the legacy composer request. The plugin owns the session: it captures the screen through the read-only CLI, records the microphone, transcribes each push-to-talk segment and injects one user message. The CLI writes no session file and takes no lease; the annotation surface changes no desktop state.

### 11.1 Session directory and files

The plugin creates `<messageDir>/annotate/<sessionId>/`, where `messageDir` is the desktop-message directory (`$XDG_STATE_HOME/hyprscope/message`, overridden by `HYPRSCOPE_MESSAGE_DIR`). `sessionId` is the trigger instant as a compact UTC stamp plus four random hex digits, for example `20261119T162512345Z-a1b2`.

| File | Writer | Purpose |
|---|---|---|
| `session.json` | plugin | Session record: `version`, `sessionId`, `mode: "annotate"`, `startedAt`, `audioStartedAt`, `state` (`ready` when the overlay may start, then `sent` or `cancelled`), `language`, `capture`, `context`, `error` |
| `capture.png` | plugin | Clean screenshot of the captured monitor; the same path is in `session.json.capture.path` |
| `audio.pcm` | plugin | Raw microphone recording: 16 kHz, mono, signed 16-bit little-endian, 32 bytes per millisecond |
| `voice-events.json` | overlay | Push-to-talk segments with absolute start and end and an optional `anchor` |
| `voice/<id>.json` | plugin | One segment's transcript: `id`, `text`, `seconds`, `error` and optional `phrases[]` |
| `annotations.json` | overlay | Annotation geometry and comments, rewritten on every change |
| `send.json` | overlay | Final submission: `overallNote`, `items[]` and `segments[]` |
| `ack.json` | plugin | Injection receipt: `ok`, `message`, `sessionId` and `at` |
| `cancel.json` | overlay | `{ version: 1, at }`; optional, written when the user cancels |
| `error.json` | plugin | `{ version: 1, message, at }`; optional, written when the session cannot continue |

`active.json` lives at `<messageDir>/annotate/active.json`, not inside a session directory: it is the entry point the overlay polls while loading, and it carries `{ version, sessionId, dir, startedAt, audioStartedAt, state }`. The plugin removes it when the session ends, so a leftover entry cannot reopen a crashed session.

Every document except `voice/<id>.json` carries `version: 1`; the plugin and the overlay ignore a document whose version or shape does not validate.

### 11.2 Time base

A session has one origin: `startedAt`, the absolute epoch-millisecond instant of the trigger. Every `at`, `atStart` and `atEnd` in `annotations.json`, `voice-events.json`, `voice/<id>.json` and `send.json` is an absolute epoch-millisecond instant from the same machine clock; the card displays `t = at - startedAt`. No relative timestamp is written to disk, so the overlay, the plugin and the CLI cannot drift apart.

`audioStartedAt` is the absolute instant of the first PCM sample and is `null` when no recorder could start. To cut audio, the plugin computes the offset from the recording start (`at - audioStartedAt`); 16 kHz mono s16le is exactly 32 bytes per millisecond, so byte offset = milliseconds × 32. Every cut is clamped to the bytes that exist.

Two documents keep their older shapes: `open.json.at` is an ISO-8601 string, and the desktop-message `ack.json.at` is also an ISO-8601 string. The annotation `ack.json.at` is epoch milliseconds, because every annotation document uses one clock.

### 11.3 Images, screen coordinates and normalization

`session.json.capture` describes the clean screenshot: `path` (absolute PNG), `width`/`height` in image (physical) pixels, `layoutRect` (`[x, y, width, height]` in Hyprland global layout coordinates), `monitor`, `scale`, `transform` and `sha256`. The plugin captures the monitor under the pointer (falling back to the focused monitor) with the read-only `screenshot --monitor` command.

The PNG is never drawn on: shapes and comments exist only as metadata. `annotations[].from` and `to` are coordinates in the PNG's own pixels, with the origin at the image's top-left. The overlay normalizes them for display by dividing by `scale` (the image is drawn at `width / scale` by `height / scale`) and converts back when writing the file. A screen point is therefore the `layoutRect` origin plus the image coordinate divided by `scale`; the intent card prints both forms. A `windowId` is resolved by hit-testing that global point against `context.windows[].rect`, which uses global layout coordinates.

`session.json.context` carries `cursor` (a global layout point or null), `focusedWindow` (an address or null), `windows[]` (at most 24 windows that intersect the capture, in z order, later entries on top) and `monitors[]`. A window record is `{ id, class, title, pid, rect, workspace, monitor, focused, floating }`; `id` is the Hyprland address, while titles and classes are mutable metadata, never identifiers.

### 11.4 Annotation records

`annotations.json.items[]` holds one record per shape: `id`, `index` (the one-based display number, reassigned when the list is reordered), `shape` (`rect`, `ellipse` or `arrow`), `from`, `to`, `atStart`, `atEnd`, `comment` and an optional `windowId` from the hit test. Comments stay in the file and on the card; they are not burned into the picture. The overlay rewrites the document atomically on every change, so a crash cannot leave half a JSON document behind.

### 11.5 Voice segments and VAD phrases

`voice-events.json.segments[]` holds one record per push-to-talk segment: `id` (`v1`, `v2`, …), `atStart`, `atEnd` and an optional `anchor` (`{ x, y, windowId?, annotationId? }`), which is the pointer position and the selected or in-progress annotation at the moment the key was pressed. The overlay writes the segment when recording starts (end equal to start) and rewrites it when recording stops.

The plugin records raw PCM for the whole session, then cuts each segment and runs a frame-energy VAD on it: 20 ms frames, a 300 ms silent run ends a phrase, phrases with less than 200 ms of voiced audio are dropped, and each phrase is padded by 200 ms on both sides (neighbouring phrases split a shared gap instead of overlapping). Every surviving phrase is transcribed separately; `voice/<id>.json` stores the segment's concatenated `text`, its `seconds`, an `error` and `phrases[]` with `{ atStart, atEnd, text }` in absolute time.

The pairing granularity is the phrase, not the whole segment: one push-to-talk segment can produce several phrases and each can bind a different annotation. When the DSH `speechToText` service is missing or a transcription fails, the file carries `error` and empty `text`; the overlay shows the failure and the user can type the words in the review card instead. A failed transcript never blocks the submission.

### 11.6 Links and confidence

The plugin pairs phrases with annotations (`linkVoiceToAnnotations`) and reports each pairing as `{ annotationIds, voiceIds, confidence, source, ambiguous }`:

| Rule | Condition | Confidence | `source` |
|---|---|---|---|
| 1 | Exactly one overlapping annotation reaches 60% of the shorter interval | 0.9 | `overlap` |
| 2 | Several annotations overlap; the largest overlap wins and the link is flagged ambiguous | 0.6 | `overlap` |
| 3 | No usable overlap, but the segment's `anchor.annotationId` names an existing annotation | 0.8 | `anchor` |
| 4 | Otherwise, the nearest annotation that starts within 2 seconds after the phrase ends | 0.5 | `sequence` |
| 5 | Nothing matches | — | no link; the phrase is a global note |

A partial overlap below 60% is not a confident temporal match and falls through to rules 3 and 4. Several phrases may bind the same annotation and keep their time order. A text `comment` and a linked phrase are both preserved; neither replaces the other. A re-binding chosen in the review card is authoritative: an explicit `send.json.segments[].annotationId` replaces the automatic pairing for every phrase of that segment with confidence 1 and source `manual`, and `null` removes the pairing so the segment is a global note.

### 11.7 Submission, receipt and degradation

On submit the overlay writes `send.json` with `version`, `sessionId`, `at` (epoch milliseconds), `overallNote`, the final `items[]` and `segments[]`. Each segment's `text` is the user's final text: for a segment with one VAD phrase it replaces the transcript, and a segment whose transcription failed becomes one typed phrase; a segment with several phrases keeps the per-phrase texts from `voice/<id>.json`, because that is the pairing granularity. The plugin waits for the transcription queue (6 seconds at most), applies the submitted text and bindings, builds the intent card and injects one prompt through the DSH Host.

On success it writes `ack.json` with `ok: true`, the DSH `sessionId` that received the prompt and `message: null` (or `"sent without the screenshot"` when the PNG could not be attached); the overlay closes 1.5 seconds later. On failure it writes `ok: false` with the error text; the overlay shows the error and keeps the annotations and transcripts so the user can retry or go back. `error.json` is the non-retryable path — the session could not be prepared — and the overlay then offers only to close.

Degradations are local and keep the session usable:

- No Wayland session or no Quickshell: `hyprscope message annotate` fails with `NO_SESSION` or `OVERLAY_FAILED` and writes no request.
- DSH not running (stale heartbeat): the command still starts the overlay and reports `dsh: "unavailable"`; the overlay shows that DSH is not running instead of opening a session.
- No `parec` and no `arecord`: `audioStartedAt` is `null`, every transcript carries an error, and the session continues with typed comments.
- No DSH `speechToText` service, or a failed transcription: the same `voice/<id>.json` error path; sending is not blocked.
- Screenshot over 8 MiB or unreadable: the prompt travels as text only and the card states that the screenshot is not attached.
- User cancel (`cancel.json`), overlay death or a quit request: the plugin stops the recorder, cleans the child processes and removes `active.json`; no microphone is left open and no prompt is injected.

### 11.8 Overlay states

The surface moves through `loading → annotating → review → sending → sent | error | cancelled`. In `loading` it polls `active.json` and `session.json` and fails after 5 seconds if DSH never prepared the session. In `annotating` it shows the frozen image, the shape toolbar, the numbering, the push-to-talk badge and the optional comment editor; Space starts and stops push-to-talk, Enter moves to `review`, and Esc asks for a cancel confirmation. In `review` the card lists the annotations and transcripts, allows editing the text and re-binding a segment, and Enter submits while Esc returns to `annotating`. In `sending` it polls `ack.json` and times out after 20 seconds; `sent` closes 1.5 seconds after the receipt, and every failure lands in `error`. The surface is hidden during `loading` so the plugin's frozen screenshot cannot contain the overlay, and it holds the keyboard exclusively only while visible.
