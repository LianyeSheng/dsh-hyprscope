# Observation and capability contract

English | [中文](/docs/PROTOCOL.zh.md)

This document fixes the meaning of the fields `hyprscope` outputs, and records the capability boundary of the control surface (`hyprscope control`). The observation layer's fields are the `dsh-cua` provider's input; the capabilities that change the desktop are exposed only through `hyprscope control`, never from the read-only commands.

Renaming a field counts as a breaking change and requires updating the tests and the README in the same change.

Read commands accept `--desktop user|agent|external` to select the instance they observe; `user` is the default and therefore also the value used when the flag is omitted. The selector grants nothing: observation stays read-only, and the default user resolution skips the recorded agent or external instance, so a running managed desktop cannot silently become the user's desktop.

## 1. Snapshot record

The top level of `state --json`:

| Field | Meaning |
|---|---|
| `readOnly` | Always `true`. Callers use it to refuse to treat this source as an executable backend |
| `observedAt` | ISO-8601 capture time |
| `session` | Discovery result: `instanceSignature`, `waylandDisplay`, `pid`, `runtimeDir`, `instanceCount`, `discovery` (`explicit`/`scan`), `waylandDisplaySource`, `inheritedEnvironment` |
| `compositor` | `name`, `version`, `branch`, `configProvider` (`lua`/`hyprlang`), `backend` |
| `isolation` | `mode: 'shared-seat'`, `seatCount` (filled only by `doctor`), `note` |
| `active` | `window`, `workspace`, `monitor` |
| `monitors` / `workspaces` / `clients` / `layers` | Normalized arrays |
| `cursor` | `{ x, y }`, global layout coordinates |
| `lock` | `{ locked: boolean \| null, source, sessionId, seat, type, reason? }` |

The stable fields of `clients[]`:

```
windowId            Hyprland window address (0x…), the unique id for later operations
app                 window class
initialApp          class at startup
title               title (mutable, not an id)
pid                 client process
monitor             monitor id (number)
workspace           { id, name }, or null
position            { x, y }, global layout coordinates
size                { width, height }, logical pixels
floating            whether the window floats
fullscreen          internal fullscreen mode: 0 normal / 1 fullscreen / 2 maximized (a number, not a boolean)
fullscreenClient    client-side fullscreen mode, encoded like fullscreen
pinned / grouped    pinned / number of windows in the group
mapped / hidden / acceptsInput / xwayland
focusHistoryId      focus-history ordinal, 0 is the most recent
stableId            stable identifier generated by Hyprland
```

`monitors[]`: `id`, `name`, `position`, `size` (including `scale`, `transform`, `refreshRate`), `focused`, `dpmsOn`, `activeWorkspace`, `specialWorkspace`, `reserved`.
`workspaces[]`: `id`, `name`, `monitor`, `windows`, `hasFullscreen`, `lastWindow`, `lastWindowTitle`, `persistent`, `layout`.
`layers[]`: one entry per surface, `monitor`, `level`, `namespace`, `pid`, `position`, `size`, `alpha`.

## 2. Coordinates and scaling

- All geometry is **global layout coordinates**, with the origin at the top-left of the layout; with multiple monitors it can be negative.
- `size` is logical pixels, not physical pixels: a 4K output with `scale = 2` has a logical size of 1920×1080.
- Screenshot resolution = the output's physical pixels. Region screenshots use global layout coordinates; `grim` accepts `X,Y WxH`, and this tool converts `x,y,w,h` into that format.
- When a monitor has a `transform` (rotation), region coordinates are still given as layout coordinates; the compositor handles the conversion.
- When pointer input is implemented later, it must use the same coordinate system; do not use the physical pixels of a screenshot directly as layout coordinates.

## 3. Event stream

`.socket2.sock` is line text in the format `event>>payload`, where the payload is comma-separated fields. `events` only parses and passes through:

```
workspace>>2
activewindow>>zen,Title
openwindow>>0x1234,2,zen,Title
closewindow>>0x1234
movewindow>>0x1234,2
monitoradded>>HDMI-A-1
```

`events` defines the match string as `event:data` (a colon), so `--match '^openwindow:'` matches only window-open events. When `--once` finds no match before the timeout it exits with code 1, which makes scripted waits convenient.

## 4. Error codes

| Code | Trigger condition | Caller handling |
|---|---|---|
| `USAGE` | Invalid arguments | Fix the arguments; exit code 2 |
| `NO_SESSION` | No instance found / no socket for the named display | Ask the user to start the compositor or pass `--signature` |
| `SESSION_GONE` | The control socket or the event socket has disconnected | Rediscover; do not retry the old handle |
| `READ_ONLY` | A command outside the allowlist was requested | Programming error; do not fall back |
| `COMMAND_FAILED` | `hyprctl`/probe exited non-zero | Look at `details.stderr`/`details.exitCode` |
| `BAD_OUTPUT` | The return is not JSON | Version incompatibility; record `details.sample` |
| `LOCKED` | The session reports locked and `--allow-locked` was not passed | Wait for the unlock; do not retry the screenshot |
| `SCREENSHOT_FAILED` | `grim` failed or produced no PNG | Check `WAYLAND_DISPLAY` and the session |
| `TIMEOUT` | Timeout | Input already sent cannot be undone (during `hyprscope control run`) |
| `CAPABILITY` | A plan or a control request needs a capability the accepted baseline does not grant, or no baseline is accepted yet | Run `hyprscope control baseline --probe`, have a human accept the result, then replan; do not retry |

## 5. Capability report

The `capabilities` of `doctor --json`:

```json
{
  "observation": ["screenshot", "events", "clients", "workspaces", "monitors", "layers", "cursor", "lockState"],
  "action": [],
  "wayland": {
    "seatCount": 1,
    "globals": [{ "interface": "zwp_virtual_keyboard_manager_v1", "version": 1 }],
    "capabilities": { "virtualKeyboard": true, "virtualPointer": true, "screencopy": true, "imageCopyCapture": true,
      "foreignToplevel": true, "workspaceManager": true, "idleNotifier": true, "sessionLock": true, "pointerWarp": true }
  }
}
```

`action` is always empty; this is the read-only entry's promise, not a pending item: `hyprscope` does not change the desktop, and control capabilities appear only under `hyprscope control` (§8, §9). A `null` `wayland` means the probe is not compiled.

### 5.1 Capability baseline

`doctor --json` also reports which desktop it observed and the capability baseline `hyprscope control` gates on for that desktop (see [COMPATIBILITY.md](/docs/COMPATIBILITY.md) and [BASELINE.md](/docs/BASELINE.md)). `doctor` only reads the accepted file: it never probes, writes, or takes a lease.

```json
{
  "target": { "kind": "agent", "signature": "…", "managed": true },
  "baseline": {
    "present": true,
    "state": "usable",
    "path": "/home/user/.local/state/hyprscope/desktop/baseline/<signature>.json",
    "approvedAt": "2026-11-17T23:12:00.000Z",
    "compositorVersion": "0.57.2",
    "target": "agent",
    "staleness": {
      "verdict": "fresh",
      "reasons": [],
      "measuredAt": "2026-11-18T00:05:00.000Z",
      "differences": []
    },
    "degraded": [],
    "missingRequired": [],
    "warnings": []
  }
}
```

`target` is the resolved desktop: `kind` is `user`, `agent` or `external`, `signature` is the live instance signature, and `managed` is true only for a recorded agent or external desktop. `baseline.target` repeats the kind the baseline belongs to. `baseline.staleness` compares that baseline with the running instance: `verdict` is `fresh`, `stale` or `unverified`; `reasons` are human sentences; `measuredAt` is the comparison time; and `differences[]` lists disagreements as `{ field, recorded, observed }`, with values as text. `staleness` is `null` when no accepted baseline exists. `stale` means a recorded value differs or the live instance could not report it; `unverified` means the baseline does not record a value the comparison needs, including an older baseline written before effective values were recorded.

`present: false` with `state: null` means control is unavailable even though observation still works; `warnings[0]` then carries the reader's reason (no file, still a draft, unreadable, or a newer schema). `missingRequired` lists required capabilities the baseline did not measure, and `degraded` lists safety paths that are absent; currently the only degraded capability is `safety.failsafe-bind`. Neither list changes `capabilities.observation` or `capabilities.action`.

The user's desktop keeps the machine-wide `baseline.json`; an agent or external desktop is keyed by its instance signature under `desktop/baseline/<signature>.json`, so one desktop's baseline cannot gate another. A `stale` or `unverified` verdict is a report here; `hyprscope control run` and `hyprscope control request` refuse it with `CAPABILITY` before any consent step.

## 6. Mapping to `dsh-cua`

`dsh-cua`'s request union lives in `packages/experimental/cua/src/protocol.ts`. "The read-only layer" here means `hyprscope` itself: the table below only says whether it can provide a method; what the control side can already do is listed in §9, and the CUA provider has not been wired up yet.

| CUA method | Can the read-only layer provide it | Notes |
|---|---|---|
| `getCapabilities` | Partially | Use `doctor`'s platform/version/isolation; `permissions` comes from the lease state (§8) |
| `listApps` / `findApps` | Yes | The `pid` in `clients[]` plus the `.desktop` file can assemble an app list |
| `listWindows` | Yes | `clients[]`, with `windowId` as the Hyprland address |
| `activate` / `show` | No | The control side already implements them with `focusWindow` / `workspace` (§9) |
| `getState` | Partially | Only window geometry and focus; no accessibility element tree (Wayland has no global AX, that needs AT-SPI) |
| `getState`'s `tree` / `elementId` | No | AT-SPI is separate work |
| `screenshot` | Yes | `grim`; returns size/sha256/path |
| `mouseMove` / `click` / `drag` / `scroll` | No | The control side already implements them through `wl-inject` (§9) |
| `pressKey` / `typeText` / `paste` | No | Keyboard injection is implemented (§9); the clipboard is not yet |
| `setValue` / `selectText` / `performAction` / `invoke` | No | Depends on the AT-SPI element tree |

Three points to watch when mapping:

1. CUA coordinates default to "the pixels of the most recent screenshot", and `relative: true` is a 0–999 per-mille value; this tool gives layout coordinates. Do the conversion in the provider and do not pollute the observation layer.
2. CUA's `snapshotId`/`elementId` have no counterpart; judge invalidation yourself from `focusHistoryId` + `windowId` when window geometry changes.
3. CUA's `appLevelAccessibility: false` is the honest value for a Linux provider; do not report true.

## 7. Version-sensitive points

- Hyprland 0.57's `dispatch` argument is a **Lua expression** (for example `hl.dsp.focus({ window = "address:0x…" })`), not the old dispatcher name; `keyword` has no effect under a Lua configuration, and configuration changes go through `eval`. The tool supports only the Lua provider: when `configProvider` is not `lua`, the whole control subset is unavailable (corresponding to `dispatch.lua` in [COMPATIBILITY.md](/docs/COMPATIBILITY.md)).
- `hyprctl -j cursorpos` returns `{"x","y"}` on 0.57; older versions may return plain text `x, y`, and the parser must tolerate that.
- The format of `hyprland.lock` is `<pid>\n<wayland-display>`; reading only the first line also works, and the display falls back to scanning.
- Event names grow with versions (`ext_workspace_manager_v1`-related ones, `screencopy`, and so on); consumers must ignore unknown events rather than error.

## 8. Control lease (`hyprscope control`)

The lease answers **control ownership**: who is in control and when it ends. The lease itself does not inject input; injection and plan execution are in §9. The observation layer's `readOnly` and `action: []` semantics therefore stay unchanged: `hyprscope` still sends no command that changes the desktop, and `doctor` still reports no control or input capability.

Read the control side's state with `hyprscope control status --json` (`phase`, remaining time, holder/overlay pid, recovery progress); the record format is in "Lease record" below.

### Lease record

The single source of truth is `$XDG_STATE_HOME/hyprlease/state.json` for the user's desktop; an agent or external desktop keeps the same record under `$XDG_STATE_HOME/hyprlease/<signature>/state.json`, selected internally by `HYPRSCOPE_LEASE_SIGNATURE`. The fields are the same:

| Field | Meaning |
|---|---|
| `leaseId` | Opaque lease id; every decision/control record must carry it |
| `phase` | `consent` / `granted` / `released` / `denied` / `expired` / `revoked` |
| `reason` | The request reason shown to the host |
| `planBound` / `planSummary` | Whether the lease approves a submitted plan, and the consent-card summary; `false` / `null` when no plan is bound |
| `attempt` / `maxResumes` | The current attempt (`0` is the original plan, `1..maxResumes` are recoveries) and the recovery count consent covers (default `1`, maximum `3`) |
| `totalBudgetMs` | The total budget counted from `createdAt`, or `null` (unbounded) |
| `renewals[]` | One `{ at, attempt, ttlMs, expiresAt }` per renewal, in time order |
| `ttlMs` | The single-hold time requested at request time; a renewal changes only `expiresAt`, not this field |
| `consentDeadline` | The consent phase deadline; when it passes the lease becomes `expired` automatically |
| `grantedAt` / `expiresAt` | Grant time and expiry time |
| `endedAt` / `endReason` | Terminal time and reason (`agent` / `host` / `shortcut` / `ttl` / `stale-owner` / `consent-timeout`) |
| `requesterPid` / `holderPid` / `overlayPid` | The three related processes; the holder is the owner after approval |

The heartbeat `heartbeat.json` is refreshed every 500ms by the requester/holder; when it has not been refreshed for more than 5 seconds the lease is treated as ownerless, and the next `status` or `request` closes the lease out as `revoked`.

### Invariants

1. Single lease: `lease.lock` is created with `O_EXCL`, and a second `request` gets `LEASE_ACTIVE`.
2. Terminal states are irreversible: after entering `released/denied/expired/revoked` the lease never returns to `granted`.
3. Record ownership: `decision.json` / `control.json` carry `leaseId`; records that do not belong to the current lease are ignored.
4. No input replay: queued actions are never executed after control is returned; input already sent cannot be undone (once injection is enabled).
5. Forced close-out: if `panic` sees no holder close-out within 5 seconds, it stops the overlay, writes the terminal state, and releases the lock itself.
6. Renewal does not re-ask for consent: `renewLease` only renews a lease that is `granted`, unexpired and has the same `leaseId`; `attempt` increments by one each time and never exceeds `maxResumes`, while `planBound` and `planSummary` stay unchanged (details in `docs/LEASE.md`).

### Failsafe shortcut

`hyprscope control install-bind` appends a marked `hl.bind(...)` to `~/.config/hypr/hyprland.lua`; its argument is `hl.dsp.exec_cmd("<绝对路径 node> <绝对路径 bin/hyprscope.ts> control panic --source shortcut")`, plus `description = "hyprscope failsafe: revoke desktop control"`. The installation flow: back up the configuration → write the block → `hyprctl reload` → verify through the `description` in `hyprctl binds -j` → on failure restore the backup and report `BIND_FAILED`.

Write the key name in Hyprland's spelling (`Escape`, not `ESC`); in 0.57 `hl.bind` records the internal index rather than the command string in `arg`, so verification can only look at `description`.

### Relationship to CUA

CUA's `click` / `typeText` and other methods are still unimplemented, and `getCapabilities().action` must not report them as available. The precondition for a future injection helper is: read the lease before every batch of actions and continue only when `phase === "granted"` and the `leaseId` matches; after a lease reaches a terminal state, reject all injection.

## 9. Plan execution (capability declaration)

`hyprscope` remains read-only. The only command that changes desktop state is `hyprscope control run <plan.json | ->`: it must hold a lease from §8 that is bound to the submitted plan (`planBound: true`). `hyprscope control install-bind` only writes the Hyprland configuration file and does not change desktop state; it is the sole exception to this rule.

Plan execution, interference prompts, the recovery model and fault records are in `docs/PLAN.md`; whether these capabilities still hold after switching machines or versions is in [COMPATIBILITY.md](/docs/COMPATIBILITY.md) (the capability baseline, implemented and gated at run time).

New capability surface:

| Capability | Wayland protocol / interface | Notes |
|---|---|---|
| Absolute/relative pointer motion | `zwlr_virtual_pointer_manager_v1` → `motion_absolute` / `motion` | Single seat, interleaved with the physical pointer |
| Pointer buttons | Same manager → `button` | Clicking absolute coordinates is a low-confidence action |
| Scroll | Same manager → `axis` + `frame` | Values in `wl_fixed` |
| Keyboard keys and text | `zwp_virtual_keyboard_manager_v1` → `keymap` / `key` / `modifiers` | Fixed US keymap, keycodes are evdev |
| Focus / workspace switching | `hyprctl dispatch '<lua 表达式>'` | The test machine's compositor uses the Lua config provider, and the `dispatch` argument is evaluated as Lua; only the allowlisted subset the executor generates is executed: `hl.dsp.focus({ workspace = … })` / `hl.dsp.focus({ window = … })` |
| Window move / size | Same subset: `hl.dsp.window.move` / `hl.dsp.window.resize` | Absolute layout coordinates (`x`/`y`; when resizing, `x`/`y` are width/height); the expression carries no `relative` field — in the Lua API a missing `relative` means absolute, and the tool never generates a relative move; when a window is fullscreen the compositor rejects both calls |
| Window float / pin | Same subset: `hl.dsp.window.float` / `hl.dsp.window.pin` | Set the state explicitly: `action = "on" \| "off"`, not a toggle |
| Window fullscreen state | Same subset: `hl.dsp.window.fullscreen_state` | `internal` / `client` each take `0` (normal) / `1` (fullscreen) / `2` (maximized), with `action = "set"` |
| Move silently to a workspace | Same subset: `hl.dsp.window.move` + `follow = false` | `follow = false` does not switch the current workspace; this is a capability of the dispatcher subset, and no plan op maps to it yet |

The plan ops `resizeWindow` (absolute `width`/`height`) and `fullscreenWindow` (`internal`/`client` modes) map to the window-size and fullscreen-state calls respectively; `floatWindow`'s `floating`/`pinned` map to explicit `on`/`off`.

The injection helper additionally requires a lease proof: `--lease-state <state.json> --lease <id>`; it re-reads the state file before each injection and rejects that command when `phase` is not `granted`, the id does not match, the lease does not approve a submitted plan (`planBound` is not `true`), or the lease has expired; `--probe` and `--dry-run` are unaffected.

Lua expressions are assembled by the executor from allowlisted templates, with variables format-checked first (window address `0x…`, workspace name `[A-Za-z0-9._-]`, coordinates are integers); no string is passed through verbatim. If the compositor returns `error:` or `warning:`, it counts as a failure.

Explicitly not provided: `exec`, `keyword`, `kill`, `plugin`, arbitrary dispatchers, arbitrary Lua, shell commands, configuration changes. The only `hyprctl reload` is in `install-bind`, used solely to make the failsafe shortcut take effect.

The plan record (`out/runs/<runId>/`) is not part of the observation contract; its fields evolve with the executor. Only the fault-record fields listed in `docs/PLAN.md` carry a stability commitment to callers.
